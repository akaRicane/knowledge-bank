TypeScript v6 — Migration guide

Breaking changes, removed compiler options, new defaults, and the catch variable narrowing pattern. Migrating from TypeScript 5.x. Released March 23, 2026 — the last JavaScript-based compiler before the Go rewrite in v7.

v6 compiler breaking changes Last updated: 2026-05-17

Overview

TypeScript 6 is the most disruptive major release since the introduction of strict mode. The two highest-impact changes are:

  1. strict: true is now the default — projects without an explicit strict setting silently gain all strict checks.
  2. types: [] is now the default — ambient globals from @types/node and similar packages disappear unless explicitly listed.

Projects that already set strict: true and explicit types (e.g. those using @adonisjs/tsconfig) are largely unaffected by these two changes. The main practical impact on AdonisJS projects is the catch variable typing described below.

strict: true by default

strict: true is shorthand for enabling all of the following flags simultaneously:

FlagWhat it catches
strictNullChecksnull and undefined not assignable to other types — must be handled explicitly.
strictFunctionTypesFunction parameters checked contravariantly — prevents unsafe function assignments.
strictBindCallApply.bind(), .call(), .apply() are type-checked instead of returning any.
strictPropertyInitializationClass properties must be initialised in the constructor or marked optional.
noImplicitAnyVariables inferred as any become errors — must be typed explicitly.
noImplicitThisthis typed as any inside functions becomes an error.
useUnknownInCatchVariablescatch (error) gives error: unknown instead of error: any.
alwaysStrictEmits "use strict" in every output file.

types: [] by default

Previously, TypeScript auto-included all installed @types/* packages. In v6, types defaults to an empty array — ambient globals from @types/node (process, Buffer, __dirname, etc.) and similar packages are no longer available unless listed explicitly. 

// tsconfig.json — required in v6 to restore @types/node globals
{
  "compilerOptions": {
    "types": ["node"]
  }
}

Projects using @adonisjs/tsconfig already declare "types": ["@types/node"] explicitly — no change needed.

Other default changes

module: esnext and target: es2025 as defaults only matter for projects that did not previously set these. AdonisJS projects use module: NodeNext explicitly, which is unaffected.

noUncheckedSideEffectImports: true means that importing a module purely for its side effects (e.g. import './polyfill') now errors if TypeScript cannot find a declaration file for it. Add a // @ts-ignore or a .d.ts shim for known side-effect-only imports that have no types.

Deprecated options

These options are deprecated in v6 and will be hard errors in v7. Using them produces a compiler error unless you add "ignoreDeprecations": "6.0" to compilerOptions as a temporary migration shim.

  }

catch variables: unknown

The useUnknownInCatchVariables flag (part of strict) types catch (error) as unknown instead of any. This was already available in TS 4.4 but becomes universally active in v6 for any project without an explicit strict: false.

The problem

try {
  await doSomething()
} catch (error) {
  // TS 5 (no strict): error is 'any' — accessing properties compiles fine
  // TS 6 (strict: true): error is 'unknown' — accessing properties is an error
  console.log(error.message) // TS18046: 'error' is of type 'unknown'
}

The fix: instanceof narrowing

The idiomatic v6 pattern is to narrow with instanceof before accessing properties. This both satisfies TypeScript and correctly surfaces unexpected errors instead of swallowing them silently. 

import { errors } from '@vinejs/vine'

try {
  await validator.validate(data)
} catch (error) {
  if (!(error instanceof errors.E_VALIDATION_ERROR)) throw error
  // TypeScript now knows error is E_VALIDATION_ERROR — properties are accessible
  console.log(error.messages)
}

Why not type assertions?

// avoid: type assertion bypasses the type system
} catch (error) {
  const e = error as MyError   // compiles but unsafe if error is something else
  console.log(e.message)
}

instanceof narrowing is preferred because it is a runtime check, not just a compile-time assertion. If the error is not what you expect, the throw error branch re-surfaces it — the test suite will catch it instead of silently passing with undefined values.

Handling unknown error shapes

// when you don't know the error type
} catch (error) {
  const message = error instanceof Error ? error.message : String(error)
  logger.error(message)
}

New features

es2025 target and lib

New built-in types for features that reached stage 4 by 2025:

  • Promise.try()
  • New Set methods: union(), intersection(), difference()
  • New Map / WeakMap methods: getOrInsert(), getOrInsertComputed()
  • Iterator helpers: .map(), .filter(), .take(), .drop()
  • RegExp.escape()
  • Temporal API (stage 4)

Native #/ subpath imports

Node.js package.json imports field (subpath imports with # prefix) is now resolved natively by the TypeScript compiler without requiring explicit paths entries. Projects using #models/*, #services/* etc. no longer need to mirror these in tsconfig.json when using moduleResolution: nodenext.

DOM lib consolidation

dom.iterable and dom.asynciterable are now bundled into the base dom lib. Projects that explicitly listed these can remove them.

--stableTypeOrdering

A diagnostic flag that forces the TS 6 compiler to emit types in the same deterministic order as the upcoming Go-based TS 7 compiler. Useful for validating that a migration from TS 6 to TS 7 will produce equivalent output.

Migration steps

Recommended order

  1. Bump typescript in devDependencies: 
    npm install --save-dev typescript@latest
  2. Run tsc --noEmit and collect all errors. The most common categories:
    • TS18046 — catch (error) is unknown → fix with instanceof narrowing
    • TS2345 / TS2322 — strict null checks surfacing new issues
    • TS2307 — @types/* globals missing → add to types
    • TS5023 — removed compiler option in use → remove it
  3. If there are many errors, add "ignoreDeprecations": "6.0" temporarily and fix errors incrementally. Remove the shim before merging.
  4. Fix catch blocks using instanceof narrowing (see above).
  5. Run the full test suite to confirm runtime behaviour is unchanged.

Checking for removed options

# tsc lists removed/unknown options as errors
npx tsc --noEmit 2>&1 | grep "TS5023\|TS5024\|TS5025"

Projects using @adonisjs/tsconfig are largely shielded from the v6 default changes because the shared config already sets all critical options explicitly:

⚠
The one real-world impact: catch variables. AdonisJS test suites commonly use assert.instanceOf(error, SomeClass) inside catch blocks and then access properties on error directly. This fails in v6 because error is unknown and assert.instanceOf() does not narrow the type at the TypeScript level. 
// before — compiles in TS 5, fails in TS 6
} catch (error) {
  assert.instanceOf(error, errors.E_VALIDATION_ERROR)
  assert.equal(error.messages[0].field, 'email') // TS18046: 'error' is of type 'unknown'
}

// after — correct in TS 6
} catch (error) {
  if (!(error instanceof errors.E_VALIDATION_ERROR)) throw error
  assert.equal(error.messages[0].field, 'email')
}

The assert.instanceOf call is removed because the instanceof guard already makes it redundant — if the error is not the expected type, the test will fail at the throw line with the original unexpected error, which is more informative than an assertion failure.
