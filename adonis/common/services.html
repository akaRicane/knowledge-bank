Backend service layer

Business logic lives in app/services/ — controllers stay thin and delegate to services. Services receive plain data, not HttpContext.

Conventions

  • One service class per domain entity (e.g., UserService).
  • Services are injected via AdonisJS's container — declare them in controller constructors.
  • Use DB transactions in services when multiple model writes must be atomic.
  • Avoid fat controllers — keep controllers to: validate → delegate to service → return response.
// backend/app/services/user_service.ts
export default class UserService {
  async alreadyExists(email: string): Promise<boolean> {
    const user = await User.findBy('email', email)
    return !!user
  }

  async create(payload: CreateUserPayload): Promise<User> {
    return await db.transaction(async (trx) => {
      const user = await User.create({
        email: payload.email,
        password: payload.password,
        emailVerificationToken: randomBytes(32).toString('hex'),
      }, { client: trx })

      await Profile.create({ userPublicId: user.publicId }, { client: trx })
      return user
    })
  }

  async generateToken(user: User): Promise<AccessToken> {
    return await User.accessTokens.create(user)
  }
}

// backend/app/controllers/users_controller.ts
export default class UsersController {
  constructor(private userService: UserService) {}

  async register({ request, response }: HttpContext) {
    const payload = await request.validateUsing(createUserValidator)
    if (await this.userService.alreadyExists(payload.email)) {
      return response.conflict({ message: 'Email already in use' })
    }
    const user = await this.userService.create(payload)
    const token = await this.userService.generateToken(user)
    return response.created({ user, token, message: 'Successfully registered user' })
  }
}

Webapp API client services

The webapp has no database. All data flows through two service classes in webapp/app/services/api/. Both read BACKEND_API_URL from the environment.

Request pattern

Both services share a private request<T>() wrapper around fetch:

type ApiResponse<T> = { data: T; status: number; ok: boolean }

private async request<T>(
  endpoint: string,
  options: RequestInit = {}
): Promise<ApiResponse<T>> {
  const url = `${this.baseUrl}${endpoint}`
  const response = await fetch(url, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      'Accept': 'application/json',
      ...(options.headers as Record<string, string>),
    },
  })
  const data = await response.json().catch(() => ({}))
  return { data: data as T, status: response.status, ok: response.ok }
}
⚠
On network failure, request() throws — it does not return { ok: false }. Callers must handle thrown errors separately from HTTP-level failures.

Route enums

Endpoint strings should not be hardcoded in services. Define them in shared enums so route strings stay in sync across services, controllers, and tests: 

// webapp/common/enums/api_routes.ts
export enum UsersAuthApiRoutes {
  REGISTER            = '/user/register',
  LOGIN               = '/user/login',
  LOGOUT              = '/user/logout',
  ME                  = '/user/me',
  UPDATE              = '/user/update',
  PROFILE_UPDATE      = '/user/profile/update',
  RESEND_VERIFICATION = '/user/resend-verification',
  RESET_PASSWORD      = '/user/reset-password',
  VERIFY_EMAIL        = '/user/verify-email',
  FORGOT_PASSWORD     = '/user/forgot-password',
