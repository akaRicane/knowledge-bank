Functional tests auto-start the HTTP server. Unit tests do not.

Session driver in tests

Set SESSION_DRIVER=memory in the test .env to avoid cookie persistence between requests.

DB cleanup pattern

Every functional test group truncates all tables before each test — not after. This gives each test a clean database state and avoids flaky cleanup on test failure. 

test.group('Artists CRUD', (group) => {
  // Runs before each individual test
  group.each.setup(() => testUtils.db('app_db').truncate())

  test('creates an artist', async ({ client }) => {
    const response = await client.post('/artists').json({
      fullName: 'Test Artist',
    })
    response.assertStatus(201)
  })
})
⚠
Use the named connection string (testUtils.db('app_db')), not the default. The connection name is defined in config/database.ts.

Functional tests

Live in tests/functional/. Each test file targets one resource or feature. Tests spin up the real HTTP server and make real database writes. 

test.group('User registration', (group) => {
  group.each.setup(() => testUtils.db('app_db').truncate())

  test('registers a user successfully', async ({ client }) => {
    const response = await client.post('/user/register').json({
      email: 'test@example.com',
      password: 'password123',
      confirmPassword: 'password123',
    })
    response.assertStatus(201)
    response.assertBodyContains({ message: 'Successfully registered user' })
  })

  test('rejects duplicate email', async ({ client }) => {
    const payload = { email: 'test@example.com', password: 'password123', confirmPassword: 'password123' }
    await client.post('/user/register').json(payload)
    const response = await client.post('/user/register').json(payload)
    response.assertStatus(409)
  })
})

Authenticated requests in functional tests

// Login first, capture the token
const loginRes = await client.post('/user/login').json({ email, password })
const token = loginRes.body().token.value

// Use the token for authenticated calls
const meRes = await client.post('/user/me').bearerToken(token)
meRes.assertStatus(200)

Unit tests

Live in tests/unit/. No HTTP server, no database. Test pure logic.

// tests/unit/models/user.spec.ts
test.group('User role methods', () => {
  test('isAdmin returns true for admin role', ({ assert }) => {
    const user = new User()
    user.userRole = UserRole.ADMIN
    assert.isTrue(user.isAdmin())
    assert.isFalse(user.isModerator())
  })
})

// tests/unit/validators/user.spec.ts
test.group('createUserValidator', () => {
  test('fails with mismatched passwords', async ({ assert }) => {
    await assert.rejects(
      () => createUserValidator.validate({
        email: 'user@example.com',
        password: 'password123',
        confirmPassword: 'different',
      })
    )
  })
})

Webapp tests

The webapp has no database. Tests either create backend fixtures via direct fetch calls to BACKEND_API_URL, or rely on seeded data. Fixtures must be cleaned up in the test body.

Inertia assertions

// Add .withInertia() to send X-Inertia: true header
const response = await client.get(`/view/${artist.publicId}`).withInertia()

response.assertStatus(200)
response.assertInertiaComponent('viewer/Viewer')
response.assertInertiaPropsContains({
  response: { ok: true, data: { type: 'artist' } }
})

Cookie extraction

Japa's API client does not automatically persist cookies between requests. Extract the oat_token from the response body and pass it manually: 

const registerRes = await client.post('/user/register').json(payload)
const oatToken = registerRes.body().token.value

// Pass the token as a cookie for subsequent requests
const meRes = await client.post('/user/me').withCookie('oat_token', oatToken)
meRes.assertStatus(200)

Running tests

# All tests (from project root)
npm run test

# Backend tests only
cd backend && node ace test

# Single suite
node ace test --suite=functional
node ace test --suite=unit

# Single test by name
node ace test -- --grep "registers a user"

# Webapp tests (starts backend automatically)
npm run test:webapp

# Webapp tests directly (backend must already be running)
cd webapp && node ace test

Test file glob — version difference

v6 — adonisrc.ts uses alternation syntax with parentheses:

tests: {
  suites: [
    {
      name: 'functional',
      files: ['tests/functional/**/*.spec(.ts|.js)'],
    },
  ],
}

v7 — glob must use brace expansion; the parenthesis form is no longer recognised:

tests: {
  suites: [
    {
      name: 'functional',
      files: ['tests/functional/**/*.spec.{ts,js}'],
    },
  ],
}
⚠
Using the v6 (.ts|.js) pattern in v7 silently matches no files — tests appear to pass with 0 tests run.

Factory usage in tests

In functional tests, prefer direct model creation over factories for clarity and speed. Factories are primarily designed for seeders. 

// Preferred in tests: direct creation
const artist = await Artist.create({ fullName: 'Test Artist' })

// Factories: use in seeders or when you need many records with realistic data
const posts = await PostFactory.createMany(10)

The exception: use factories in tests when you need complex relationship fixtures (e.g., a user with a profile) that would require multiple explicit create calls.
