Models

Lucid ORM models, the ULID public ID pattern, relationship conventions, factories, seeders, and migration ordering.

lucid orm postgresql Last updated: 2026-05-14

ULID public ID pattern

Every model has two identifiers: an internal auto-increment id (never exposed) and a publicId — a 26-character ULID used in all API responses and URLs. 

import { ulid } from 'ulid'

@beforeCreate()
static async generatePublicId(model: BaseModel): Promise {
  if (!model.publicId) {
    model.publicId = ulid()
  }
}
ℹ
The if (!model.publicId) guard means seeders can set a known ULID for reproducible data, and the hook won't overwrite it.

Viewer endpoint pattern

A GET /view/:publicId endpoint can resolve any model by ULID, returning { type: 'artist' | 'venue' | 'concert' | 'profile', data: ... }. This allows a single URL pattern to deep-link to any entity.

Serialization rules

Sensitive columns use serializeAs: null to exclude them from JSON output:

@column({ serializeAs: null })
declare password: string

@column({ serializeAs: null })
declare emailVerificationToken: string | null

@column({ serializeAs: null })
declare passwordResetToken: string | null

Never expose id, password, token fields, or internal keys. Always use publicId as the external identifier.

Relationship patterns

hasOne / belongsTo with a non-PK foreign key

When the foreign key references a column other than id, both sides of the relationship must declare it explicitly: 

// User model — has one Profile, linked by publicId (not id)
@hasOne(() => Profile, {
  localKey: 'publicId',
  foreignKey: 'userPublicId',
})
declare profile: HasOne<typeof Profile>

// Profile model — belongs to User
@belongsTo(() => User, {
  localKey: 'userPublicId',   // column on Profile
  foreignKey: 'publicId',     // column on User
})
declare user: BelongsTo<typeof User>
⚠
The localKey/foreignKey semantics are swapped between the two sides. On belongsTo, localKey is the column on the child model and foreignKey is the column on the parent.

manyToMany with pivot table

@manyToMany(() => Artist, {
  pivotTable: 'concert_artists',
})
declare artists: ManyToMany<typeof Artist>

Pivot tables use composite primary keys: (concert_id, artist_id). Both FKs cascade on delete.

ON DELETE SET NULL

When a parent can be deleted independently of children (e.g., a venue can be deleted and its concerts remain), use ON DELETE SET NULL on the FK rather than CASCADE.

Factories

All factories live in database/factories/.

// Defining a factory
export const UserFactory = factory
  .define(User, ({ faker }) => ({
    email: faker.internet.email(),
    password: 'password123',
    userRole: faker.helpers.enumValue(UserRole),
    emailIsVerified: Math.random() > 0.8,
  }))
  .relation('profile', () => ProfileFactory)
  .build()

Tests vs seeders Factories are primarily for seeders. In tests, prefer direct model creation (Post.create({...})) for clarity.

Seeders

Always run through an orchestrator seeder to control dependency order. Individual seeders are not order-safe on their own. 

# From project root (recommended)
npm run seed

# Or directly
node ace db:seed --files="database/seeders/main_seeder.ts"

Orchestrator pattern

// database/seeders/main_seeder.ts
export default class MainSeeder extends BaseSeeder {
  async run() {
    await new UserSeeder(this.client).run()    // 1. users (no deps)
    await new CategorySeeder(this.client).run()// 2. categories (no deps)
    await new PostSeeder(this.client).run()    // 3. posts (needs users + categories)
  }
}

Include at least one named/known fixture per seeder alongside random factory-generated records so tests can rely on predictable data.

Migrations

Use naturalSort: true in config/database.ts so migrations run in timestamp order. Create migrations in dependency order — parent tables before child tables.

Enum types in PostgreSQL

Create PostgreSQL enum types in the migration with raw queries, then use them in columns:

// In the migration up() method
await db.rawQuery(`CREATE TYPE user_role AS ENUM ('admin', 'moderator', 'default')`)
table.enum('user_role', null, {
  useNative: true,
  enumName: 'user_role',
  existingType: true,
}).defaultTo('default').notNullable()

Rollback safety

Always implement the down() method. For enum types, drop them in the down migration:

async down() {
  await schema.dropTable('users')
  await db.rawQuery('DROP TYPE IF EXISTS user_role')
}
