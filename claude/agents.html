Agents

Specialized subagents registered in .claude/agents/. Each agent has a specific mission and output format. Claude Code selects them automatically based on their description, or they can be invoked explicitly.

code-architect

Model: sonnet  ·  Color: green

Designs feature architectures by analyzing existing codebase patterns and conventions, then produces a complete implementation blueprint. Use before implementing any non-trivial feature to ensure the approach integrates cleanly with existing code.

Process

  1. Extract existing patterns, conventions, architectural decisions, and module boundaries from the codebase.
  2. Make a decisive architectural choice — one recommendation, not a menu.
  3. Specify every file to create or modify, component responsibilities, and integration points.

Deliverables

  • Patterns and conventions found (with file:line references)
  • Chosen architecture with rationale and trade-offs
  • Component designs with responsibilities and dependencies
  • Implementation map — specific files and what changes in each
  • Complete data flow
  • Build sequence as a checklist
  • Critical details: error handling, state management, testing, security

code-explorer

Model: sonnet  ·  Color: yellow

Deeply analyzes an existing feature by tracing execution paths, mapping architecture layers, and documenting dependencies. Use when you need to understand an unfamiliar part of the codebase before making changes.

Process

  1. Find entry points (APIs, UI components, CLI commands) and core implementation files.
  2. Follow call chains, trace data transformations, identify dependencies, document side effects.
  3. Map abstraction layers: presentation → business logic → data.
  4. Document algorithms, data structures, error handling, and edge cases.

Deliverables

  • Entry points with file:line references
  • Step-by-step execution flow with data transformations
  • Key components and their responsibilities
  • Architecture insights (patterns, layers, design decisions)
  • Dependencies (external and internal)
  • List of essential files to understand the feature

code-simplifier

Model: opus  ·  Color: green

Simplifies recently written or modified code for clarity, consistency, and maintainability while preserving all functionality. Auto-triggered after completing a coding task. Only refines recently modified code unless instructed otherwise.

Principles

  • Preserve functionality — only changes how code does things, not what it does.
  • Apply project standards from CLAUDE.md (import patterns, naming, error handling).
  • Reduce nesting, eliminate redundancy, improve naming, avoid nested ternaries.
  • Avoid over-simplification that reduces maintainability.

comment-analyzer

Model: inherit  ·  Color: green

Analyzes code comments for accuracy, completeness, and long-term maintainability. Use after generating large documentation comments or before finalizing PRs with comments. Never modifies code directly — only provides feedback.

What it checks

  • Factual accuracy — cross-references every comment claim against actual code.
  • Completeness — sufficient context without being redundant.
  • Long-term value — will this comment still be useful in 2 years?
  • Misleading elements — ambiguous language, outdated references, incorrect assumptions.

Output

  • Summary of scope and findings
  • Critical Issues (factually incorrect or highly misleading)
  • Improvement Opportunities
  • Recommended Removals
  • Positive Findings

code-reviewer

Model: opus  ·  Color: green

Reviews code for adherence to project guidelines (CLAUDE.md) and detects actual bugs. By default reviews unstaged changes from git diff. Uses a confidence ≥ 80 threshold — only reports issues it is highly confident about.

Review scope

  • Project guidelines compliance — import patterns, framework conventions, naming, error handling, testing, logging.
  • Bug detection — logic errors, null/undefined handling, race conditions, memory leaks, security, performance.
  • Code quality — duplication, missing error handling, accessibility, test coverage gaps.

Confidence scoring (0–100)

ScoreMeaning
≥ 80Reported — highly confident, real issue
50–79Not reported — real but too nitpicky
< 50Not reported — likely false positive

Output

Grouped by severity (Critical → Important) with: description, file:line reference, CLAUDE.md rule citation, concrete fix.

pr-test-analyzer

Model: inherit  ·  Color: cyan

Reviews pull requests for test coverage quality and completeness. Focuses on behavioral coverage — not line coverage. Each recommendation is rated 1–10 for criticality.

What it looks for

  • Untested error handling
  • Missing edge cases
  • Uncovered business logic
  • Missing negative tests
  • Absent async behavior tests

Criticality ratings

RatingSeverity
9–10Critical — data loss, security, system failures
7–8Important — user-facing errors
5–6Edge cases — confusion, minor issues
3–4Nice-to-have
1–2Minor improvements

silent-failure-hunter

Model: inherit  ·  Color: yellow

Reviews code changes for silent failures, inadequate error handling, and inappropriate fallback behavior. Invoke proactively after any work involving error handling or catch blocks.

Core principles

  • Silent failures are unacceptable in production.
  • Users deserve actionable feedback — not generic errors.
  • Fallbacks must be explicit and justified.
  • Catch blocks must be specific — never catch Exception or Error broadly.
  • Mock/fake implementations belong only in tests.

What it scans

  • Empty catch blocks
  • Catch-then-continue patterns
  • Returning null on error instead of throwing
  • Optional chaining used as error suppression
  • Retry exhaustion without user notification

Output per issue

Location (file:line), severity (CRITICAL / HIGH / MEDIUM), issue description, hidden errors list, user impact, recommendation, corrected code example.

type-design-analyzer

Model: inherit  ·  Color: pink

Analyzes type design in the codebase. Use when introducing new types, during PR creation, or when refactoring existing types. Rates four dimensions on a 1–10 scale.

Four rated dimensions

DimensionWhat it measures
EncapsulationHidden implementation details, appropriate access modifiers, minimal interface
Invariant ExpressionClarity through type structure, compile-time enforcement, self-documentation
Invariant UsefulnessPrevents real bugs, aligned with business requirements
Invariant EnforcementChecked at construction, all mutation points guarded, impossible invalid states

Key principles

  • Prefer compile-time guarantees over runtime checks.
  • Types should make illegal states unrepresentable.
  • Constructor validation is crucial.
  • Value clarity over cleverness.

Agent file template

Place in .claude/agents/my-agent.md:

---
name: my-agent
description: One-line description. Claude Code reads this to decide when to use the agent automatically.
model: sonnet
color: green
---

# My Agent

## Mission
What this agent exists to do — one clear paragraph.

## Process
1. First step — what to analyze or read
2. Second step — what to produce
3. ...

## Output format
- Bullet describing what the agent returns
- Include file:line references where applicable
- Include severity ratings if reviewing
