HTTP Methods

Semantics, idempotency, body conventions, and expected response codes for each method.

http Last updated: 2026-05-14

Overview

HTTP methods describe the intent of a request. Choosing the correct method matters for cacheability, idempotency, and client interoperability — not just convention.

Method Safe Idempotent Request body Typical success code
GET ✓ ✓ No 200
POST ✗ ✗ Yes 201 / 200
PUT ✗ ✓ Yes 200 / 204
PATCH ✗ ✗ (usually) Yes 200 / 204
DELETE ✗ ✓ Rarely 204 / 200
HEAD ✓ ✓ No 200
OPTIONS ✓ ✓ No 204 / 200

Safe — the request has no side effects. Clients and proxies may retry or cache freely.
Idempotent — sending the same request multiple times produces the same result as sending it once.

GET

Retrieve a resource or a collection. The request must have no side effects.

Rules

  • Never modify state in a GET handler.
  • Do not send a request body — it is technically allowed by HTTP but ignored by most servers and clients.
  • Filter/sort parameters belong in the query string, not the body.
  • Responses are cacheable by default unless Cache-Control: no-store is set.

Response codes

CodeWhen to use
200 OKResource found and returned.
304 Not ModifiedConditional GET — resource hasn't changed since If-None-Match / If-Modified-Since.
404 Not FoundResource does not exist.
401 UnauthorizedAuthentication required.
403 ForbiddenAuthenticated but not permitted.

Example

GET /posts?page=2&limit=20 HTTP/1.1
Accept: application/json

POST

Create a new resource, or trigger an action that doesn't map cleanly to CRUD (e.g. POST /auth/login, POST /payments/refund).

Rules

  • Not idempotent — calling POST twice creates two resources (unless you implement idempotency keys).
  • On successful creation, return 201 Created with a Location header pointing to the new resource.
  • For action-style endpoints (not resource creation), 200 OK is acceptable.
  • Validate the request body and return 422 Unprocessable Entity on validation failure.

Response codes

CodeWhen to use
201 CreatedNew resource created. Include Location: /posts/42.
200 OKAction succeeded and response body is meaningful (e.g. login returning a token).
202 AcceptedRequest queued for async processing; result not yet known.
400 Bad RequestMalformed request (invalid JSON, missing required field).
409 ConflictResource already exists (e.g. duplicate email on registration).
422 Unprocessable EntityBody is valid JSON but fails business validation rules.

Example

POST /posts HTTP/1.1
Content-Type: application/json

{
  "title": "Hello world",
  "body": "First post."
}

---

HTTP/1.1 201 Created
Location: /posts/ulid_01j2k3m
Content-Type: application/json

{ "id": "ulid_01j2k3m", "title": "Hello world" }

PUT

Replace a resource in its entirety. The client sends the complete desired state — any fields not included are treated as absent (or set to their defaults).

Rules

  • Idempotent — calling PUT twice with the same body has the same effect as calling it once.
  • The client must send all fields, not just the changed ones. If the client only knows some fields, use PATCH instead.
  • If the resource doesn't exist and your API allows creation via PUT, return 201 Created. Otherwise return 404.
  • Return 204 No Content if there's nothing useful to return, or 200 OK with the updated resource.

Response codes

CodeWhen to use
200 OKReplaced and returning the updated resource.
204 No ContentReplaced successfully, no body needed.
201 CreatedResource didn't exist and was created (upsert).
404 Not FoundResource doesn't exist and upsert is not supported.
422 Unprocessable EntityValidation failed on the replacement body.

Example

PUT /posts/42 HTTP/1.1
Content-Type: application/json

{
  "title": "Updated title",
  "body": "Full replacement body."
}

---

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "42", "title": "Updated title", "body": "Full replacement body." }

PATCH

Apply a partial update to a resource. Only the fields included in the body are changed; others remain untouched.

Rules

  • PATCH is not required to be idempotent by the spec, but your implementation should strive for it when possible.
  • Only include fields the client wants to change. Never require the full resource body.
  • To explicitly clear a field, send null. Omitting a field means "leave unchanged."
  • Prefer PATCH over PUT when clients don't have the full resource state (e.g. updating a single setting).
ℹ
PATCH vs PUT — use PUT when the client owns the full state of the resource. Use PATCH when the client only knows what changed.

Response codes

CodeWhen to use
200 OKUpdated and returning the full updated resource.
204 No ContentUpdated successfully, no body needed.
404 Not FoundResource doesn't exist.
422 Unprocessable EntityPatch body fails validation.

Example

PATCH /users/me HTTP/1.1
Content-Type: application/json

{ "bio": "New bio text." }

---

HTTP/1.1 200 OK
Content-Type: application/json

{ "id": "42", "name": "Alice", "bio": "New bio text.", "email": "..." }

DELETE

Remove a resource. Idempotent — deleting an already-deleted resource should not return an error.

Rules

  • Idempotent: a second DELETE on the same resource should return 204 (or 404 — pick one and be consistent).
  • Do not include a response body unless you need to return metadata (e.g. a deletion receipt). Prefer 204 No Content.
  • Avoid sending a request body. Pass the resource identifier in the URL path.
  • For soft deletes, consider whether DELETE is the right verb — or whether PATCH to a status: "archived" field is more accurate.

Response codes

CodeWhen to use
204 No ContentDeleted successfully. No body.
200 OKDeleted and returning a confirmation body (e.g. deleted resource snapshot).
404 Not FoundResource not found. Acceptable if you choose not to be fully idempotent.
409 ConflictCannot delete due to a dependency constraint (e.g. deleting a category that has posts).

Example

DELETE /posts/42 HTTP/1.1
Authorization: Bearer <token>

---

HTTP/1.1 204 No Content

HEAD

Identical to GET, but the server must not return a response body. Used to check existence, validate a cache, or read metadata before fetching.

When to use

  • Check if a resource exists before a full GET (avoids downloading the body).
  • Read Content-Length to decide whether to stream or paginate.
  • Validate ETag / Last-Modified for cache freshness.
✓
If your GET handler is implemented correctly, HEAD should work automatically — the framework strips the body. You shouldn't need a separate HEAD route.

OPTIONS

Ask the server which methods and headers are allowed for a resource. Browsers send a preflight OPTIONS request automatically before cross-origin requests with custom headers.

CORS preflight

OPTIONS /api/posts HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: Content-Type, Authorization

---

HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, PATCH, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Max-Age: 86400

Most frameworks handle OPTIONS preflights automatically when CORS middleware is configured. You typically don't need to define OPTIONS routes manually.

Choosing the right method

Decision guide

IntentMethodNotes
Read a resource / list GET Always. No exceptions.
Create a new resource POST Return 201 + Location header.
Replace a resource completely PUT Client must send all fields.
Update some fields of a resource PATCH Only changed fields in the body.
Remove a resource DELETE Prefer 204, no body.
Trigger an action (login, send, publish) POST Use a verb-noun URL: POST /auth/login.
Bulk update PATCH PATCH /posts with an array body.
Bulk delete DELETE DELETE /posts with IDs in body or query.

Common mistakes

  • Using POST for everything — safe, idempotent reads should be GET so they can be cached and retried.
  • Using GET with a body — put filter params in the query string. If the query is too complex, use POST /search.
  • Returning 200 for all responses — use 201 for creation, 204 for no-content deletes. Clients rely on these codes.
  • Confusing PUT and PATCH — PUT with partial data silently clears missing fields on many server implementations.
