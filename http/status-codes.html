HTTP Status Codes

When to use each code, what it means to clients, and the mistakes to avoid.

http Last updated: 2026-05-14

Overview

Status codes communicate the outcome of a request at the protocol level. Clients — browsers, mobile apps, API consumers — rely on these codes to decide whether to retry, redirect, prompt for login, or surface an error. Using the wrong code forces clients to inspect the body instead of the header.

RangeClassMeaning
1xxInformationalRequest received, continuing process.
2xxSuccessRequest understood and fulfilled.
3xxRedirectionFurther action needed to complete the request.
4xxClient errorThe request is wrong — fix it before retrying.
5xxServer errorThe server failed — the client can retry later.

2xx — Success

200 OK

The request succeeded. The response body contains the result.

  • Use for successful GET, PATCH, and PUT responses that include a body.
  • Also use for action-style POST endpoints that return data (login, search, etc.).
  • Do not use for resource creation — use 201 instead.

201 Created

A new resource was successfully created.

  • Always pair with a Location header pointing to the new resource URL.
  • The response body can include the created resource or be empty.
  • Only for POST (and PUT when creating via upsert).
HTTP/1.1 201 Created
Location: /posts/01jwb3k5n2
Content-Type: application/json

{ "id": "01jwb3k5n2", "title": "Hello world" }

202 Accepted

The request was received and will be processed asynchronously. The result is not yet known.

  • Use when work is queued (background jobs, email delivery, exports).
  • Include a way for the client to check status: a polling URL in Location or a job ID in the body.
  • Do not imply success — the job could still fail.
HTTP/1.1 202 Accepted
Content-Type: application/json

{ "jobId": "job_abc123", "statusUrl": "/jobs/job_abc123" }

204 No Content

The request succeeded, and there is no body to return.

  • Typical for DELETE and for PUT/PATCH when you don't need to return the updated resource.
  • The response must have no body — not even an empty JSON object.
  • Also used for OPTIONS preflight responses.

206 Partial Content

The server is returning only part of the resource, as requested by a Range header.

  • Used for media streaming, large file downloads, and resumable uploads.
  • Requires a Content-Range header in the response.
  • Rarely needed in application APIs — more common in file-serving infrastructure.

3xx — Redirects

CodeNameMethod preserved?Use case
301 Moved Permanently No — GET only Resource has permanently moved. Browsers and search engines update the cached URL.
302 Found No — GET only Temporary redirect. Browsers always GET the new URL regardless of the original method.
303 See Other No — always GET After a POST, redirect to a result page. The browser GETs the new URL (Post/Redirect/Get pattern).
304 Not Modified — Conditional GET — client's cached version is still valid. No body returned.
307 Temporary Redirect Yes Temporary redirect that preserves the original method (POST stays POST).
308 Permanent Redirect Yes Permanent redirect preserving the method. Use instead of 301 for non-GET redirects.
ℹ
301 / 302 change the method to GET. If you redirect a POST and the destination must also receive a POST, use 307 (temporary) or 308 (permanent) instead.

4xx — Client Errors

The request is wrong. The client should fix the request before retrying. Do not retry 4xx responses automatically — they will fail again.

400 Bad Request

The request is malformed and the server cannot parse or process it.

  • Invalid JSON syntax, missing Content-Type header, unparseable query params.
  • Do not use for business logic failures (wrong password, duplicate email) — use 401, 409, or 422.
  • Use 400 for structural problems; use 422 for semantic/validation problems.

401 Unauthorized

Authentication is required and has failed or was not provided.

  • The name is misleading — it means "unauthenticated", not "unauthorized".
  • Return a WWW-Authenticate header indicating the auth scheme.
  • The client should prompt the user to log in and retry.
  • Do not use when the user is logged in but lacks permission — use 403.
HTTP/1.1 401 Unauthorized
WWW-Authenticate: Bearer realm="api"
Content-Type: application/json

{ "error": "Authentication required." }

403 Forbidden

The client is authenticated but does not have permission to access this resource.

  • The user is known, but not allowed. Do not reveal whether the resource exists if that would leak information — prefer 404 in sensitive contexts.
  • Retrying with the same credentials will not help.

404 Not Found

The requested resource does not exist at this URL.

  • Also use to hide the existence of a resource for security (instead of 403).
  • On a route that previously existed but was removed, consider 410 Gone instead.
  • Return a helpful body explaining what wasn't found when possible.

405 Method Not Allowed

The HTTP method used is not supported for this endpoint.

  • Must include an Allow header listing the supported methods.
  • Usually generated automatically by the router — check your framework's behavior.
HTTP/1.1 405 Method Not Allowed
Allow: GET, POST, HEAD

409 Conflict

The request conflicts with the current state of the resource.

  • Duplicate unique value (email already registered, slug taken).
  • Optimistic concurrency conflict (stale ETag or version mismatch).
  • Trying to delete a resource that has dependent records.
  • The body should explain the conflict so the client can resolve it.

410 Gone

The resource existed but has been permanently removed and will not be available again.

  • More informative than 404 — clients and search engines should remove any references.
  • Use for soft-deleted or retired resources when you want to signal permanence.

422 Unprocessable Entity

The request body is syntactically valid but fails business validation rules.

  • The right code for form/API validation errors — not 400.
  • Return a structured error body with field-level details.
  • The client must fix the input before retrying.
HTTP/1.1 422 Unprocessable Entity
Content-Type: application/json

{
  "errors": [
    { "field": "email", "message": "Email is already in use." },
    { "field": "password", "message": "Password must be at least 8 characters." }
  ]
}

429 Too Many Requests

The client has sent too many requests in a given time window (rate limiting).

  • Include a Retry-After header (seconds or an HTTP date) so the client knows when to retry.
  • Optionally include X-RateLimit-Limit and X-RateLimit-Remaining headers.
HTTP/1.1 429 Too Many Requests
Retry-After: 30
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0

5xx — Server Errors

The server failed to fulfill a valid request. The client is not at fault. 5xx responses are safe to retry (with backoff) unless the operation is non-idempotent.

⚠
Never expose internal error details (stack traces, SQL errors, file paths) in 5xx responses. Log them server-side and return a generic message to the client.

500 Internal Server Error

An unexpected error occurred on the server. It's a catch-all for unhandled exceptions.

  • Log the full error server-side with a correlation ID.
  • Return the correlation ID in the response so it can be referenced in support.
  • Do not expose stack traces or implementation details.
HTTP/1.1 500 Internal Server Error
Content-Type: application/json

{ "error": "An unexpected error occurred.", "ref": "err_01jwb3k" }

502 Bad Gateway

The server, acting as a gateway or proxy, received an invalid response from an upstream server.

  • Indicates the upstream service (API, microservice, database proxy) is down or returning garbage.
  • The gateway itself is functional — the upstream is not.
  • Usually generated by a reverse proxy (nginx, Caddy) rather than application code.

503 Service Unavailable

The server is temporarily unavailable — overloaded or undergoing maintenance.

  • Include a Retry-After header if the downtime is known.
  • Use during planned maintenance windows or circuit-breaker open states.
  • Clients and load balancers use this to route traffic away from the failing instance.

504 Gateway Timeout

The gateway or proxy timed out waiting for an upstream response.

  • The upstream server did not respond within the timeout window.
  • Distinct from 503: the server is reachable, but too slow.
  • Consider whether the original request was processed — retrying a non-idempotent operation may cause a duplicate.

Error response body

Adopt a consistent error body shape across your API. Clients should be able to programmatically extract the error without parsing a string.

Recommended shape

{
  "error": "Human-readable summary.",
  "code":  "MACHINE_READABLE_CODE",
  "fields": {
    "email": ["Email is already in use."],
    "name":  ["Name is required."]
  },
  "ref": "err_01jwb3k"
}
FieldRequiredPurpose
errorYesShort human-readable summary. Safe to display to users.
codeRecommendedMachine-readable constant for programmatic handling (e.g. EMAIL_TAKEN).
fieldsFor 422 onlyField-level validation messages. Key = field name, value = array of messages.
refFor 5xx onlyCorrelation ID for log lookup. Never expose stack traces here.
